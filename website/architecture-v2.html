Architecture

Rhei is a shared-nothing, disaggregated-state streaming engine. A #[rhei::pipeline] compiles to a Timely Dataflow graph that runs on blocking threads, bridged to async Tokio sources and sinks via bounded mpsc channels. All data flows as Apache Arrow RecordBatch buffers — there is no row-by-row execution path.

The core design principle is separation of compute from state. Workers are stateless: they read through a tiered storage hierarchy (RAM → NVMe → S3) rather than owning local state. This means you can scale compute up or down without migrating data, and any worker can resume from any checkpoint.

Data enters the pipeline through an async Source (Kafka, file, etc.) that produces typed RheiBuffer<T> — an Arrow RecordBatch paired with a boolean selection vector for zero-copy filtering. The buffer is type-erased to ErasedBuffer (schema ID + raw batch) for transport through Timely’s dataflow graph, then recovered back to the typed buffer before reaching your operator’s process() method.

When a pipeline calls .key_by(), Rhei splits each buffer’s rows by seahash(key) % num_workers into per-worker sub-buffers, then routes them via Timely’s Exchange pact. Cross-worker serialization uses Arrow IPC — self-describing and columnar-native, no schema registry required.

Operators implement StreamFunction, an async trait: process(RheiBuffer<I>, &mut OperatorContext) → BufferOutput<O>. Three processing granularities are supported: row-level iteration via zero-copy View<’a> references, batch-level access to the full RecordBatch for windowed aggregations, and column-level Arrow compute kernels with selection vectors for vectorized filter expressions.

State is accessed through OperatorContext, which exposes a StateContext backend and the typed KeyedState<K, V> wrapper. Under the hood, state reads walk a three-tier hierarchy. The hot path — key present in the L1 memtable — completes in ~1μs with no I/O. An L1 miss falls through to the L2 Foyer HybridCache on local NVMe (~1ms), avoiding a network round-trip. Only on a double miss does the system reach L3 SlateDB backed by S3 (~50ms). This is transparent to operator code: the same state.get(key).await call works regardless of which tier serves it.

State values are returned as Bytes — no cloning on the hot path. The L1 memtable is a HashMap<Bytes, Bytes> with compaction and eviction policies to bound RAM usage. Each operator’s state is namespaced with a prefix ({operator_name}/{user_key}, or p{pid}/w{idx}/{operator}/{key} in multi-process mode) to prevent cross-operator interference.

Checkpointing is coordinated, not per-operator. When the Timely frontier advances past epoch N, every worker flushes its dirty L1 keys down through SlateDB to S3, then signals readiness. The coordinator (process 0 in multi-process mode) waits for all workers, merges their manifests, writes the combined manifest to S3, and only then commits source offsets. This ensures exactly-once delivery semantics: if a worker crashes after flushing state but before offset commit, the next restart will re-process from the last committed offset against already-flushed state (idempotent).

Recovery is straightforward: cargo run -- --from-checkpoint s3://bucket/checkpoints/epoch-42.json loads the manifest, seeks each Kafka partition to the checkpointed offset, and resumes processing. The --offset-delta flag adjusts offsets for local replay against re-indexed test data.

Process layers:

  PipelineController  ─── config, lifecycle, CLI (#[rhei::pipeline])
       │
       ▼
  TaskManager         ─── spawn sources/sinks, manage channels
       │
       ▼
  DataflowExecutor    ─── per-worker Timely DAG, spawn_blocking

Sources and sinks run as Tokio tasks — they’re inherently async (Kafka polling, HTTP flushes, file I/O). Timely Dataflow, however, is a synchronous runtime that expects to own its threads. Rhei bridges the two with bounded tokio::sync::mpsc channels: the source task produces RheiBuffer<T> into a channel, Timely’s spawn_blocking thread consumes from it. Backpressure propagates naturally — when the Timely side is slow, the channel fills, and the async source suspends.

The #[rhei::pipeline] proc macro generates the full process scaffolding: a #[tokio::main] entrypoint, a clap CLI with --workers, --from-checkpoint, --process-id, --peers, and --metrics-addr flags, environment variable integration, and the PipelineController → TaskManager → DataflowExecutor construction. Your pipeline function just receives a &DataflowGraph reference and builds the topology.

Clustering in Rhei has three modes, all using the same pipeline code. In multi-thread mode (.with_workers(4)), Timely spawns N worker threads in a single process with in-memory channels for exchange. In multi-process mode (.from_env()), N processes communicate over TCP using Timely’s built-in networking layer. Each process independently opens SlateDB against the same S3 bucket. Checkpoint coordination happens out-of-band: process 0 collects readiness signals from all processes before writing the merged manifest.

The third mode — dynamic clustering with Chitchat gossip for discovery and OpenRaft for consensus — is planned but not yet implemented. It will add live topology changes (add/remove workers), automatic state repartitioning, and leader election for the coordinator role.

Error handling is explicit and non-silent. Each operator has an ErrorPolicy: either Skip (log and drop the failed element) or SendToDlq (route to a DlqSink implementation). The DlqSink trait is pluggable — ship with FileDlqSink, LogDlqSink, or KafkaDlqSink, or implement your own. Critically, DLQ write errors and sink send errors are propagated, never silently swallowed. Operators can also implement an on_error() hook for custom recovery logic.

Graceful shutdown follows a strict sequence: drain in-flight batches → flush L1 state → write final checkpoint → commit source offsets → exit. This guarantees no data loss and enables clean restarts without reprocessing.
