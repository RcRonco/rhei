# Walkthrough: Building a Pipeline

A step-by-step build of one realistic pipeline. Each step is a complete, compiled program — every Rust block on this page is compiled by CI as a doctest, so you can copy any of them and they will build.

We will build **temperature monitoring for a fleet of sensors**:

1. [Define the data](#step-1-define-your-data) — schemas and views
2. [Move data end to end](#step-2-source-to-sink) — source, sink, controller
3. [Filter and transform](#step-3-filter-and-transform) — closures over views
4. [Partition by key](#step-4-partition-by-key) — `key_by` and why it must come first
5. [Add state](#step-5-add-state) — a custom operator that remembers
6. [Window over event time](#step-6-window-over-event-time) — tumbling aggregation
7. [Collect and assert](#step-7-test-it) — testing without infrastructure
8. [Run it for real](#step-8-run-it) — workers, checkpoints, metrics

The finished program is [`rhei/examples/walkthrough.rs`](../rhei/examples/walkthrough.rs); run it with `cargo run -p rhei --example walkthrough`.

Prerequisites: Rust 1.85+, and a checkout of this repository (Rhei is not published to crates.io).

## Step 1: Define your data

Stream elements are structs deriving `RheiSchema`. The derive generates three things you will use by name:

- `ReadingBuilder` — the columnar builder, via `Reading::builder(capacity)`
- `ReadingView<'a>` — a zero-copy row reference
- `ReadingColumns<'a>` — typed column accessors

```rust,no_run
#[derive(Clone, rhei::RheiSchema)]
struct Reading {
    sensor_id: String,
    celsius: f64,
    timestamp: u64,
}
```

Supported field types include `String`, `bool`, the integer and float primitives, `Option<T>` for nullable columns, and `Vec<T>` for list columns.

**`String` itself is not a stream element.** There is no `RheiSchema` impl for bare primitives — if you are streaming lines of text, wrap them:

```rust,no_run
#[derive(Clone, rhei::RheiSchema)]
struct Line {
    text: String,
}
```

### Views borrow, they do not own

This is the single most important thing to internalise. A `String` column reads back as `&'a str`, borrowed straight out of the Arrow buffer:

```rust,ignore
// not-compiled: generated by the derive; redeclaring it would collide.
struct ReadingView<'a> {
    sensor_id: &'a str,
    celsius: f64,
    timestamp: u64,
}
```

Nothing is copied until you ask. That is why the examples below call `.to_string()` explicitly — you pay for the allocation where you choose to, not on every row.

## Step 2: Source to sink

The smallest useful pipeline. `DataflowGraph` holds the topology; `PipelineController` runs it.

```rust,no_run
use rhei::{DataflowGraph, PipelineController, PrintSink, VecSource};

#[derive(Clone, rhei::RheiSchema)]
struct Reading {
    sensor_id: String,
    celsius: f64,
    timestamp: u64,
}

#[tokio::main]
async fn main() -> anyhow::Result<()> {
    let readings = vec![
        Reading { sensor_id: "boiler-1".into(), celsius: 68.0, timestamp: 1_000 },
        Reading { sensor_id: "boiler-2".into(), celsius: 91.5, timestamp: 1_100 },
        Reading { sensor_id: "boiler-1".into(), celsius: 72.4, timestamp: 2_000 },
    ];

    let graph = DataflowGraph::new();
    graph
        .source(VecSource::new(readings))
        .sink(PrintSink::<Reading>::new());

    let dir = std::env::temp_dir().join("rhei_walkthrough_step2");
    std::fs::create_dir_all(&dir)?;

    PipelineController::builder()
        .checkpoint_dir(&dir)
        .build()?
        .run(graph)
        .await?;
    Ok(())
}
```

Three things to note:

- `VecSource::new(items)` batches at 1024 rows by default; `.with_batch_size(n)` overrides it.
- `build()` returns `anyhow::Result<PipelineController>` — the `?` is required.
- `run()` returns when every source is exhausted.

The graph is validated before execution. Forget the sink and you get `dataflow graph has no sinks — every stream must end with .sink(...)` rather than a silent hang.

## Step 3: Filter and transform

Closures receive views. `filter_fn` takes `&View` and returns `bool`; `map` takes `View` and returns a new schema type.

```rust,no_run
use rhei::{DataflowGraph, PrintSink, VecSource};

#[derive(Clone, rhei::RheiSchema)]
struct Reading {
    sensor_id: String,
    celsius: f64,
    timestamp: u64,
}

#[derive(Clone, rhei::RheiSchema)]
struct Alert {
    sensor_id: String,
    message: String,
    timestamp: u64,
}

fn build(graph: &DataflowGraph) {
    graph
        .source(VecSource::new(vec![Reading {
            sensor_id: "boiler-1".into(),
            celsius: 91.5,
            timestamp: 1_000,
        }]))
        .filter_fn(|r| r.celsius > 90.0)
        .map(|r| Alert {
            sensor_id: r.sensor_id.to_string(),
            message: format!("overheating at {:.1}C", r.celsius),
            timestamp: r.timestamp,
        })
        .name("overheat_alerts")
        .sink(PrintSink::<Alert>::new());
}
```

`filter_fn` does not copy anything — it builds a boolean selection mask over the batch, and downstream operators skip masked-out rows.

### Column expressions

For simple comparisons there is a second form that runs as an Arrow compute kernel over the whole column rather than row by row:

```rust,no_run
use rhei::{DataflowGraph, PrintSink, VecSource, col, lit_f64};

#[derive(Clone, rhei::RheiSchema)]
struct Reading {
    sensor_id: String,
    celsius: f64,
}

fn build(graph: &DataflowGraph) {
    graph
        .source(VecSource::new(vec![Reading {
            sensor_id: "boiler-1".into(),
            celsius: 91.5,
        }]))
        .filter(col("celsius").gt(lit_f64(90.0)))
        .sink(PrintSink::<Reading>::new());
}
```

`filter` takes an `Expr`; `filter_fn` takes a closure. Prefer `filter` when the predicate is a plain column comparison, `filter_fn` when it needs real Rust.

### Other stateless transforms

| Method | Purpose |
|--------|---------|
| `flat_map` | One row in, many out — returns `Vec<O>` |
| `inspect` | Side effects (logging) without changing the stream |
| `distinct_by` | Drop rows whose derived key was already seen |
| `limit` | Stop after N rows |
| `batch` | Re-batch rows to a target size |
| `name` | Label the node for the TUI graph and logs |
| `merge` | Combine two streams of the same type |

## Step 4: Partition by key

Before any stateful operator, decide which worker owns which key:

```rust,no_run
use rhei::{DataflowGraph, PrintSink, VecSource};

#[derive(Clone, rhei::RheiSchema)]
struct Reading {
    sensor_id: String,
    celsius: f64,
}

fn build(graph: &DataflowGraph) {
    graph
        .source(VecSource::new(vec![Reading {
            sensor_id: "boiler-1".into(),
            celsius: 68.0,
        }]))
        .key_by(|r| r.sensor_id.to_string())
        .sink(PrintSink::<Reading>::new());
}
```

The closure returns a `String`. Every row with the same key lands on the same worker, chosen through the key group of that string — see [exchange-and-partitioning.md](exchange-and-partitioning.md).

> **This is the step it is easiest to get wrong.** Rhei has no `KeyedStream`
> type, so `.operator()` compiles on an unkeyed stream. It runs, too — and with
> more than one worker each worker sees an arbitrary slice of every key, so
> counters undercount and windows fire on partial data. Nothing errors. **Always
> `key_by` before `operator`**, and make the key match what the operator uses
> for its state.

## Step 5: Add state

Now a real operator: track each sensor's reading count and peak temperature, and emit an alert the first time a sensor exceeds its threshold.

```rust,no_run
use rhei::arrow::{
    BufferOutput, OperatorContext, RheiBuffer, RheiBuilder, RheiSchema, StreamFunction,
};
use rhei::KeyedState;

#[derive(Clone, rhei::RheiSchema)]
struct Reading {
    sensor_id: String,
    celsius: f64,
    timestamp: u64,
}

#[derive(Clone, rhei::RheiSchema)]
struct Alert {
    sensor_id: String,
    message: String,
    timestamp: u64,
}

#[derive(Clone)]
struct OverheatDetector {
    threshold: f64,
}

#[async_trait::async_trait]
impl StreamFunction for OverheatDetector {
    type Input = Reading;
    type Output = Alert;

    async fn process(
        &mut self,
        input: RheiBuffer<Reading>,
        ctx: &mut OperatorContext,
    ) -> anyhow::Result<BufferOutput<Alert>> {
        let mut builder = Alert::builder(input.len());
        let mut peaks = KeyedState::<String, f64>::new(&mut ctx.state, "peak");

        for view in &input {
            let sensor_id = view.sensor_id.to_string();
            let previous_peak = peaks.get(&sensor_id).await?.unwrap_or(f64::MIN);

            if view.celsius > previous_peak {
                peaks.put(&sensor_id, &view.celsius)?;
            }

            // Alert on the transition only, not on every hot reading.
            if view.celsius > self.threshold && previous_peak <= self.threshold {
                builder.append(Alert {
                    sensor_id,
                    message: format!("crossed {:.1}C", self.threshold),
                    timestamp: view.timestamp,
                });
            }
        }

        Ok(BufferOutput::Single(RheiBuffer::from_builder(builder)))
    }
}
```

The details the compiler will enforce, and that trip people up:

| Rule | Why |
|------|-----|
| `#[derive(Clone)]` on the operator | `.operator()` clones it once per worker |
| `state.get(&key)` takes `&K` | A `&str` view field needs `.to_string()` first |
| `state.put(..)?` returns `Result` | Serialization can fail; it is not infallible |
| Return `BufferOutput::Single(RheiBuffer::from_builder(b))` | There is no `BufferOutput::from_builder` |
| Build with `T::builder(capacity)` | Needs `RheiSchema` in scope for the trait method |

`KeyedState` is created per batch and borrows `ctx.state` — create it inside `process`, not as a struct field.

### Less boilerplate: `#[rhei::op]`

If your operator has no configuration fields, the macro writes the impl for you. It derives `Clone` and `Debug`, and names the struct after the function in PascalCase (`overheat_detector` → `OverheatDetector`):

```rust,no_run
use rhei::arrow::{BufferOutput, OperatorContext, RheiBuffer, RheiBuilder, RheiSchema};
use rhei::KeyedState;

#[derive(Clone, rhei::RheiSchema)]
struct Reading {
    sensor_id: String,
    celsius: f64,
    timestamp: u64,
}

#[derive(Clone, rhei::RheiSchema)]
struct Counted {
    sensor_id: String,
    seen: u64,
}

#[rhei::op]
async fn count_readings(
    input: RheiBuffer<Reading>,
    ctx: &mut OperatorContext,
) -> anyhow::Result<BufferOutput<Counted>> {
    let mut builder = Counted::builder(input.len());
    let mut counts = KeyedState::<String, u64>::new(&mut ctx.state, "seen");

    for view in &input {
        let sensor_id = view.sensor_id.to_string();
        let seen = counts.get(&sensor_id).await?.unwrap_or(0) + 1;
        counts.put(&sensor_id, &seen)?;
        builder.append(Counted { sensor_id, seen });
    }

    Ok(BufferOutput::Single(RheiBuffer::from_builder(builder)))
}
```

Use the trait directly when the operator needs configuration (like `threshold` above); use the macro when it does not.

## Step 6: Window over event time

Aggregate per sensor over fixed 60-second windows. Window operators are built with `::new(...)` and positional closures — **there is no builder**.

```rust,no_run
use rhei::{DataflowGraph, PrintSink, TumblingWindow, VecSource};

#[derive(Clone, rhei::RheiSchema)]
struct Reading {
    sensor_id: String,
    celsius: f64,
    timestamp: u64,
}

#[derive(Clone, rhei::RheiSchema)]
struct WindowStats {
    sensor_id: String,
    window_start: u64,
    window_end: u64,
    count: u64,
    mean_celsius: f64,
}

fn build(graph: &DataflowGraph) {
    let window = TumblingWindow::new(
        60_000, // window size, same unit as time_fn output (millis here)
        // key_fn: which key does this row belong to?
        |view: ReadingView<'_>| view.sensor_id.to_string(),
        // time_fn: the row's event time
        |view: ReadingView<'_>| view.timestamp,
        // accumulate_fn: fold each row into the accumulator
        |acc: &mut (u64, f64), view: ReadingView<'_>| {
            acc.0 += 1;
            acc.1 += view.celsius;
        },
        // finish_fn: turn the accumulator into an output row
        |key: &str, window_start: u64, window_end: u64, acc: &(u64, f64)| WindowStats {
            sensor_id: key.to_string(),
            window_start,
            window_end,
            count: acc.0,
            #[allow(clippy::cast_precision_loss)]
            mean_celsius: if acc.0 == 0 { 0.0 } else { acc.1 / acc.0 as f64 },
        },
    )
    .with_allowed_lateness(5_000);

    graph
        .source(VecSource::new(vec![Reading {
            sensor_id: "boiler-1".into(),
            celsius: 68.0,
            timestamp: 1_000,
        }]))
        .key_by(|r| r.sensor_id.to_string())
        .operator("temp_window", window)
        .sink(PrintSink::<WindowStats>::new());
}
```

The accumulator type is inferred from `accumulate_fn` and must implement `Default` — here `(u64, f64)`. There is no built-in `Avg` or `Sum`; you express the aggregation in the closure.

Windows close when the **watermark** passes `window_end + allowed_lateness`, which for a `VecSource` happens when the source is exhausted. See [time-and-watermarks.md](time-and-watermarks.md) for how the watermark actually advances, and [operators.md](operators.md) for the other window types.

## Step 7: Test it

Rhei ships no test harness — no `TestSource`, no `CollectSink`. Pair `VecSource` with a sink that collects into a shared `Vec`. This is the pattern used throughout `rhei-runtime/tests/`:

```rust,no_run
use std::sync::{Arc, Mutex};

use rhei::arrow::{RheiBuffer, Sink};
use rhei::{DataflowGraph, PipelineController, VecSource};

#[derive(Clone, rhei::RheiSchema)]
struct Reading {
    sensor_id: String,
    celsius: f64,
}

#[derive(Clone)]
struct CollectSink {
    rows: Arc<Mutex<Vec<String>>>,
}

#[async_trait::async_trait]
impl Sink for CollectSink {
    type Input = Reading;

    async fn write_batch(&mut self, batch: RheiBuffer<Reading>) -> anyhow::Result<()> {
        let mut rows = self.rows.lock().expect("lock poisoned");
        for view in &batch {
            rows.push(view.sensor_id.to_string());
        }
        Ok(())
    }
}

#[tokio::main]
async fn main() -> anyhow::Result<()> {
    let rows = Arc::new(Mutex::new(Vec::new()));

    let graph = DataflowGraph::new();
    graph
        .source(VecSource::new(vec![
            Reading { sensor_id: "hot".into(), celsius: 95.0 },
            Reading { sensor_id: "cold".into(), celsius: 12.0 },
        ]))
        .filter_fn(|r| r.celsius > 90.0)
        .sink(CollectSink { rows: Arc::clone(&rows) });

    // A fresh checkpoint dir per test, so runs never restore each other's state.
    let dir = tempfile::tempdir()?;
    PipelineController::builder()
        .checkpoint_dir(dir.path())
        .build()?
        .run(graph)
        .await?;

    assert_eq!(*rows.lock().expect("lock poisoned"), vec!["hot".to_string()]);
    Ok(())
}
```

Two habits worth keeping:

- **A fresh checkpoint directory per test.** Reusing one means the second run restores the first run's state and your assertions drift.
- **Assert unordered when workers > 1.** Sinks write per worker, so row order across workers is not deterministic. Sort, or compare as a set.

## Step 8: Run it

Everything so far used `PipelineController` directly. For a real binary, `#[rhei::pipeline]` generates `main`, the Tokio runtime, and a CLI:

```rust,no_run
use rhei::{PrintSink, VecSource};

#[derive(Clone, rhei::RheiSchema)]
struct Reading {
    sensor_id: String,
    celsius: f64,
}

#[rhei::pipeline]
fn main(graph: &DataflowGraph) {
    graph
        .source(VecSource::new(vec![Reading {
            sensor_id: "boiler-1".into(),
            celsius: 68.0,
        }]))
        .key_by(|r| r.sensor_id.to_string())
        .sink(PrintSink::<Reading>::new());
}
```

That binary now accepts:

```bash
cargo run -- --workers 4
cargo run -- --checkpoint-dir /var/lib/rhei --metrics-addr 0.0.0.0:9090
RHEI_WORKERS=4 cargo run
```

Every flag has a matching `RHEI_*` environment variable: `--workers`, `--checkpoint-dir`, `--metrics-addr`, `--process-id`, `--peers`, `--from-checkpoint`, `--offset-delta`, `--pipeline-name`.

With `--metrics-addr` set you get `/healthz`, `/readyz`, `/metrics` (Prometheus), and `/api/metrics`. See [deployment.md](deployment.md).
