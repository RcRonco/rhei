# Walkthrough: Building a Pipeline

A step-by-step build of one realistic pipeline. Each step is a complete, compiled program — every Rust block on this page is compiled by CI as a doctest, so you can copy any of them and they will build.

We will build **clickstream analytics for a web property**:

1. [Define the data](#step-1-define-your-data) — schemas and views
2. [Move data end to end](#step-2-source-to-sink) — source, sink, controller
3. [Filter and transform](#step-3-filter-and-transform) — closures over views
4. [Partition by user](#step-4-partition-by-user) — `key_by` and why it must come first
5. [Add state](#step-5-add-state) — a funnel tracker that remembers where each user got to
6. [Window into sessions](#step-6-window-into-sessions) — gap-based aggregation over event time
7. [Collect and assert](#step-7-test-it) — testing without infrastructure
8. [Run it for real](#step-8-run-it) — workers, checkpoints, metrics

The finished program is [`rhei/examples/walkthrough.rs`](../rhei/examples/walkthrough.rs); run it with `cargo run -p rhei --example walkthrough`.

Prerequisites: Rust 1.85+, and a checkout of this repository (Rhei is not published to crates.io).

---

## Step 1: Define your data

Stream elements are structs deriving `RheiSchema`. The derive generates three things you will use by name:

- `PageViewBuilder` — the columnar builder, via `PageView::builder(capacity)`
- `PageViewView<'a>` — a zero-copy row reference
- `PageViewColumns<'a>` — typed column accessors

```rust,no_run
#[derive(Clone, rhei::RheiSchema)]
struct PageView {
    user_id: String,
    path: String,
    ts: u64,
}
```

Supported field types include `String`, `bool`, the integer and float primitives, `Option<T>` for nullable columns, and `Vec<T>` for list columns.

**`String` itself is not a stream element.** There is no `RheiSchema` impl for bare primitives — if you are streaming lines of text, wrap them:

```rust,no_run
#[derive(Clone, rhei::RheiSchema)]
struct LogLine {
    text: String,
}
```

### Views borrow, they do not own

This is the single most important thing to internalise. A `String` column reads back as `&'a str`, borrowed straight out of the Arrow buffer:

```rust,ignore
// not-compiled: generated by the derive; redeclaring it would collide.
struct PageViewView<'a> {
    user_id: &'a str,
    path: &'a str,
    ts: u64,
}
```

Nothing is copied until you ask. That is why the examples below call `.to_string()` explicitly — you pay for the allocation where you choose to, not on every row.

## Step 2: Source to sink

The smallest useful pipeline. `DataflowGraph` holds the topology; `PipelineController` runs it.

```rust,no_run
use rhei::{DataflowGraph, PipelineController, PrintSink, VecSource};

#[derive(Clone, rhei::RheiSchema)]
struct PageView {
    user_id: String,
    path: String,
    ts: u64,
}

#[tokio::main]
async fn main() -> anyhow::Result<()> {
    let views = vec![
        PageView { user_id: "alice".into(), path: "/product".into(), ts: 60_000 },
        PageView { user_id: "bob".into(), path: "/product".into(), ts: 120_000 },
        PageView { user_id: "alice".into(), path: "/cart".into(), ts: 240_000 },
    ];

    let graph = DataflowGraph::new();
    graph
        .source(VecSource::new(views))
        .sink(PrintSink::<PageView>::new());

    let dir = std::env::temp_dir().join("rhei_walkthrough_step2");
    std::fs::create_dir_all(&dir)?;

    PipelineController::builder()
        .checkpoint_dir(&dir)
        .build()?
        .run(graph)
        .await?;
    Ok(())
}
```

Three things to note:

- `VecSource::new(items)` batches at 1024 rows by default; `.with_batch_size(n)` overrides it.
- `build()` returns `anyhow::Result<PipelineController>` — the `?` is required.
- `run()` returns when every source is exhausted.

The graph is validated before execution. Forget the sink and you get `dataflow graph has no sinks — every stream must end with .sink(...)` rather than a silent hang.

## Step 3: Filter and transform

Closures receive views. `filter_fn` takes `&View` and returns `bool`; `map` takes `View` and returns a new schema type.

Real clickstream is full of traffic you do not want in your analytics — health checks, monitoring probes, asset requests:

```rust,no_run
use rhei::{DataflowGraph, PrintSink, VecSource};

#[derive(Clone, rhei::RheiSchema)]
struct PageView {
    user_id: String,
    path: String,
    ts: u64,
}

#[derive(Clone, rhei::RheiSchema)]
struct Hit {
    user_id: String,
    section: String,
    ts: u64,
}

fn build(graph: &DataflowGraph) {
    graph
        .source(VecSource::new(vec![PageView {
            user_id: "alice".into(),
            path: "/product/shoes".into(),
            ts: 60_000,
        }]))
        .filter_fn(|v| !v.path.starts_with("/health"))
        .map(|v| Hit {
            user_id: v.user_id.to_string(),
            // "/product/shoes" -> "product"
            section: v.path.split('/').nth(1).unwrap_or("root").to_string(),
            ts: v.ts,
        })
        .name("hits")
        .sink(PrintSink::<Hit>::new());
}
```

`filter_fn` does not copy anything — it builds a boolean selection mask over the batch, and downstream operators skip masked-out rows.

### Column expressions

For simple comparisons there is a second form that runs as an Arrow compute kernel over the whole column rather than row by row:

```rust,no_run
use rhei::{DataflowGraph, PrintSink, VecSource};

#[derive(Clone, rhei::RheiSchema)]
struct PageView {
    user_id: String,
    path: String,
    ts: u64,
}

fn build(graph: &DataflowGraph) {
    graph
        .source(VecSource::new(vec![PageView {
            user_id: "alice".into(),
            path: "/product".into(),
            ts: 60_000,
        }]))
        // Drop anything before the campaign started.
        .filter(PageView::col().ts().gt_eq(60_000_u64))
        .sink(PrintSink::<PageView>::new());
}
```

`PageView::col()` comes from `#[derive(RheiSchema)]` and returns a typed handle
per field, so the column name and the literal's type are both checked at compile
time. There is an untyped spelling — `col("ts").gt_eq(lit_u64(60_000))` — that
takes any string, and reports a bad column or literal only when the first batch
arrives; prefer the typed form.

`filter` takes an `Expr`; `filter_fn` takes a closure. Prefer `filter` when the predicate is a plain column comparison, `filter_fn` when it needs real Rust.

### Other stateless transforms

| Method | Purpose |
|--------|---------|
| `flat_map` | One row in, many out — returns `Vec<O>` |
| `inspect` | Side effects (logging) without changing the stream |
| `distinct_by` | Drop rows whose derived key was already seen |
| `limit` | Stop after N rows |
| `batch` | Re-batch rows to a target size |
| `name` | Label the node for the TUI graph and logs |
| `merge` | Combine two streams of the same type |

## Step 4: Partition by user

Before any stateful operator, decide which worker owns which key. For clickstream that is almost always the user:

```rust,no_run
use rhei::{DataflowGraph, PrintSink, VecSource};

#[derive(Clone, rhei::RheiSchema)]
struct PageView {
    user_id: String,
    path: String,
    ts: u64,
}

fn build(graph: &DataflowGraph) {
    graph
        .source(VecSource::new(vec![PageView {
            user_id: "alice".into(),
            path: "/product".into(),
            ts: 60_000,
        }]))
        .key_by(|v| v.user_id.to_string())
        .sink(PrintSink::<PageView>::new());
}
```

The closure returns a `String`. Every row with the same key lands on the same worker, chosen through the key group of that string — see [exchange-and-partitioning.md](exchange-and-partitioning.md).

> **This is the step it is easiest to get wrong.** Rhei has no `KeyedStream`
> type, so `.operator()` compiles on an unkeyed stream. It runs, too — and with
> more than one worker each worker sees an arbitrary slice of every user's
> views, so a funnel tracker never sees a complete journey and sessions split
> into fragments. Nothing errors. **Always `key_by` before `operator`**, and
> make the key match what the operator uses for its state.

## Step 5: Add state

Now a real operator: track each user's progress through the checkout funnel `/product` → `/cart` → `/checkout`, and emit a conversion the first time someone completes it.

State is what makes this possible. A conversion is not a property of one page view — it depends on what that user did earlier.

```rust,no_run
use rhei::arrow::{
    BufferOutput, OperatorContext, RheiBuffer, RheiBuilder, RheiSchema, StreamFunction,
};
use rhei::KeyedState;

#[derive(Clone, rhei::RheiSchema)]
struct PageView {
    user_id: String,
    path: String,
    ts: u64,
}

#[derive(Clone, rhei::RheiSchema)]
struct Conversion {
    user_id: String,
    ts: u64,
}

#[derive(Clone)]
struct FunnelTracker;

impl FunnelTracker {
    fn step(path: &str) -> Option<u8> {
        match path {
            "/product" => Some(1),
            "/cart" => Some(2),
            "/checkout" => Some(3),
            _ => None,
        }
    }

    const FINAL_STEP: u8 = 3;
}

#[async_trait::async_trait]
impl StreamFunction for FunnelTracker {
    type Input = PageView;
    type Output = Conversion;

    async fn process(
        &mut self,
        input: RheiBuffer<PageView>,
        ctx: &mut OperatorContext,
    ) -> anyhow::Result<BufferOutput<Conversion>> {
        let mut builder = Conversion::builder(input.len());
        let mut furthest = KeyedState::<String, u8>::new(&mut ctx.state, "funnel_step");

        for view in &input {
            let Some(step) = FunnelTracker::step(view.path) else {
                continue;
            };

            let user_id = view.user_id.to_string();
            let reached = furthest.get(&user_id).await?.unwrap_or(0);

            // One step at a time: landing on /checkout from a bookmark, with no
            // cart, is not a funnel completion.
            if step == reached + 1 {
                furthest.put(&user_id, &step)?;

                if step == FunnelTracker::FINAL_STEP {
                    builder.append(Conversion {
                        user_id,
                        ts: view.ts,
                    });
                }
            }
        }

        Ok(BufferOutput::Single(RheiBuffer::from_builder(builder)))
    }
}
```

Because the furthest step is stored per user, a reload of `/checkout` does not convert twice — `step == reached + 1` is false the second time. That is the whole point of keyed state: the decision depends on history, not on the current row.

The details the compiler will enforce, and that trip people up:

| Rule | Why |
|------|-----|
| `#[derive(Clone)]` on the operator | `.operator()` clones it once per worker |
| `state.get(&key)` takes `&K` | A `&str` view field needs `.to_string()` first |
| `state.put(..)?` returns `Result` | Serialization can fail; it is not infallible |
| Return `BufferOutput::Single(RheiBuffer::from_builder(b))` | There is no `BufferOutput::from_builder` |
| Build with `T::builder(capacity)` | Needs `RheiSchema` in scope for the trait method |

`KeyedState` is created per batch and borrows `ctx.state` — create it inside `process`, not as a struct field.

### Less boilerplate: `#[rhei::op]`

If your operator has no configuration fields, the macro writes the impl for you. It derives `Clone` and `Debug`, and names the struct after the function in PascalCase (`count_views` → `CountViews`):

```rust,no_run
use rhei::arrow::{BufferOutput, OperatorContext, RheiBuffer, RheiBuilder, RheiSchema};
use rhei::KeyedState;

#[derive(Clone, rhei::RheiSchema)]
struct PageView {
    user_id: String,
    path: String,
    ts: u64,
}

#[derive(Clone, rhei::RheiSchema)]
struct ViewCount {
    user_id: String,
    total: u64,
}

#[rhei::op]
async fn count_views(
    input: RheiBuffer<PageView>,
    ctx: &mut OperatorContext,
) -> anyhow::Result<BufferOutput<ViewCount>> {
    let mut builder = ViewCount::builder(input.len());
    let mut totals = KeyedState::<String, u64>::new(&mut ctx.state, "views");

    for view in &input {
        let user_id = view.user_id.to_string();
        let total = totals.get(&user_id).await?.unwrap_or(0) + 1;
        totals.put(&user_id, &total)?;
        builder.append(ViewCount { user_id, total });
    }

    Ok(BufferOutput::Single(RheiBuffer::from_builder(builder)))
}
```

Use the trait directly when the operator needs configuration; use the macro when it does not.

## Step 6: Window into sessions

A *session* is a burst of activity separated from the next by a gap of inactivity — exactly what `SessionWindow` computes. Unlike tumbling windows, the boundaries come from the data, not from a fixed grid.

```rust,no_run
use rhei::{DataflowGraph, PrintSink, VecSource, Window};

const MINUTE: u64 = 60_000;

#[derive(Clone, rhei::RheiSchema)]
struct PageView {
    user_id: String,
    path: String,
    ts: u64,
}

#[derive(Clone, rhei::RheiSchema)]
struct SessionSummary {
    user_id: String,
    started_at: u64,
    ended_at: u64,
    views: u64,
}

fn build(graph: &DataflowGraph) {
    // Close a session after 30 minutes of inactivity. The builder names each
    // closure, so nothing here depends on argument order.
    let window = Window::session(30 * MINUTE)
        .key(|v: PageViewView<'_>| v.user_id.to_string())
        .time(|v: PageViewView<'_>| v.ts)
        .accumulate(|acc: &mut u64, _v: PageViewView<'_>| *acc += 1)
        .finish(
            |user_id: &str, started_at: u64, ended_at: u64, views: &u64| SessionSummary {
                user_id: user_id.to_string(),
                started_at,
                ended_at,
                views: *views,
            },
        )
        .build();

    graph
        .source(VecSource::new(vec![PageView {
            user_id: "alice".into(),
            path: "/product".into(),
            ts: MINUTE,
        }]))
        .key_by(|v| v.user_id.to_string())
        .operator("session_window", window)
        .sink(PrintSink::<SessionSummary>::new());
}
```

The accumulator type is inferred from `accumulate_fn` and must implement `Default` — here a plain `u64` counter. There is no built-in `Count` or `Sum`; you express the aggregation in the closure.

A session closes in one of two ways: a new event arrives for that user more than `gap` after the last one, or the **watermark** advances past `last_event + gap`. For a `VecSource` the second case happens when the source is exhausted. See [time-and-watermarks.md](time-and-watermarks.md) for how the watermark actually advances, and [operators.md](operators.md) for tumbling, sliding, and count windows.

## Step 7: Test it

Rhei ships no test harness — no `TestSource`, no `CollectSink`. Pair `VecSource` with a sink that collects into a shared `Vec`. This is the pattern used throughout `rhei-runtime/tests/`:

```rust,no_run
use std::sync::{Arc, Mutex};

use rhei::arrow::{RheiBuffer, Sink};
use rhei::{DataflowGraph, PipelineController, VecSource};

#[derive(Clone, rhei::RheiSchema)]
struct PageView {
    user_id: String,
    path: String,
    ts: u64,
}

#[derive(Clone)]
struct CollectSink {
    rows: Arc<Mutex<Vec<String>>>,
}

#[async_trait::async_trait]
impl Sink for CollectSink {
    type Input = PageView;

    async fn write_batch(&mut self, batch: RheiBuffer<PageView>) -> anyhow::Result<()> {
        let mut rows = self.rows.lock().expect("lock poisoned");
        for view in &batch {
            rows.push(view.user_id.to_string());
        }
        Ok(())
    }
}

#[tokio::main]
async fn main() -> anyhow::Result<()> {
    let rows = Arc::new(Mutex::new(Vec::new()));

    let graph = DataflowGraph::new();
    graph
        .source(VecSource::new(vec![
            PageView { user_id: "alice".into(), path: "/cart".into(), ts: 60_000 },
            PageView { user_id: "monitoring".into(), path: "/health".into(), ts: 61_000 },
        ]))
        .filter_fn(|v| !v.path.starts_with("/health"))
        .sink(CollectSink { rows: Arc::clone(&rows) });

    // A fresh checkpoint dir per test, so runs never restore each other's state.
    let dir = tempfile::tempdir()?;
    PipelineController::builder()
        .checkpoint_dir(dir.path())
        .build()?
        .run(graph)
        .await?;

    assert_eq!(*rows.lock().expect("lock poisoned"), vec!["alice".to_string()]);
    Ok(())
}
```

Two habits worth keeping:

- **A fresh checkpoint directory per test.** Reusing one means the second run restores the first run's state and your assertions drift.
- **Assert unordered when workers > 1.** Sinks write per worker, so row order across workers is not deterministic. Sort, or compare as a set.

The finished [`walkthrough.rs`](../rhei/examples/walkthrough.rs) does exactly this for both branches, and asserts that alice converts once despite reloading `/checkout`, and that the filtered-out `/health` traffic produces no session at all.

## Step 8: Run it

Everything so far used `PipelineController` directly. For a real binary, `#[rhei::pipeline]` generates `main`, the Tokio runtime, and a CLI:

```rust,no_run
use rhei::{PrintSink, VecSource};

#[derive(Clone, rhei::RheiSchema)]
struct PageView {
    user_id: String,
    path: String,
    ts: u64,
}

#[rhei::pipeline]
fn main(graph: &DataflowGraph) {
    graph
        .source(VecSource::new(vec![PageView {
            user_id: "alice".into(),
            path: "/product".into(),
            ts: 60_000,
        }]))
        .key_by(|v| v.user_id.to_string())
        .sink(PrintSink::<PageView>::new());
}
```

That binary now accepts:

```bash
cargo run -- --workers 4
cargo run -- --checkpoint-dir /var/lib/rhei --metrics-addr 0.0.0.0:9090
RHEI_WORKERS=4 cargo run
```

Every flag has a matching `RHEI_*` environment variable: `--workers`, `--checkpoint-dir`, `--metrics-addr`, `--process-id`, `--peers`, `--from-checkpoint`, `--offset-delta`, `--pipeline-name`.

With `--metrics-addr` set you get `/healthz`, `/readyz`, `/metrics` (Prometheus), and `/api/metrics`. See [deployment.md](deployment.md).
